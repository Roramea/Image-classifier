# 代码解耦重构方案

## Context

项目采用 MVP 架构（View → Presenter → Service → Core），但存在若干分层违反和耦合问题。审查发现 11 个问题，其中包括一个**隐藏功能 bug**：`DuplicateDetailDialog` 通过 `self.parent().classifier` 访问核心服务，但 `MainWindow` 根本没有 `classifier` 属性（只有 `presenter`），导致该代码路径永远不执行——通过详情对话框删除重复图片时，已处理记忆不会被保存，下次扫描会重复出现。

本次重构目标：
1. 修复分层违反，确保 UI 层不直接访问 Core/Service 内部状态
2. 修复 `DuplicateDetailDialog` 导致的功能 bug
3. 清理死代码（未使用的 Observer 事件）
4. 为所有修改的方法和分层边界公共 API 添加中文注释

## 修复方案（按优先级排序）

### 步骤 1：DuplicateDetailDialog 解耦 + 修复隐藏 bug（问题 1+2+4 联动）

**文件**：`dialogs/duplicate_detail_dialog.py`、`presenters/main_presenter.py`、`views/main_window.py`

**问题**：
- 对话框 `delete_selected()` 直接调用 `os.remove()` 删除文件（UI 执行业务操作）
- 对话框通过 `self.parent().classifier.add_processed_duplicate()` 反向访问核心服务（且此代码因 MainWindow 无 classifier 属性而永远不执行）
- Presenter 的 `on_duplicate_detail_closed` 直接 `del self.duplicate_service.duplicates[md5_hash]` 修改服务内部字典

**修复**：对话框只收集用户选择并返回，删除操作由 Presenter 委托给 `DuplicateService.delete_selected_duplicates()`（此方法已存在，完整处理文件删除、记忆保存、状态更新）。

`DuplicateDetailDialog` 修改：
- 新增 `self._pending_deletions: list = []` 存储确认删除的 `(md5_hash, [selected_paths])` 列表
- `delete_selected()` 移除 `os.remove` 和 `parent().classifier` 访问，改为整理选中项到 `_pending_deletions` 后 `self.accept()`
- 新增 `get_deletion_result() -> list` 返回 `_pending_deletions`

`MainWindow.show_duplicate_detail_dialog` 修改：
- 对话框 `Accepted` 时调用 `get_deletion_result()` 获取删除列表，传给回调

`MainPresenter.on_duplicate_detail_closed` 修改：
- 接收 `deletions: list`（而非 `result, selected_md5s`）
- 循环调用 `self.duplicate_service.delete_selected_duplicates(md5, paths)` 执行删除
- 处理失败路径提示、更新 UI、检查是否全部处理完成

**效果**：一次修复 3 个问题 + 1 个功能 bug。

### 步骤 2：StorageCleanDialog 解耦（问题 3）

**文件**：`dialogs/storage_clean_dialog.py`、`views/main_window.py`、`presenters/main_presenter.py`

**问题**：对话框直接接收 `classifier` 实例并调用其方法。

**修复**：对话框改为接收纯数据（`storage_size`、`storage_details`），返回选中类别列表，由 Presenter 执行清理。

`StorageCleanDialog.__init__` 改为 `(self, storage_size: int, storage_details: dict, parent=None)`，移除 `self.classifier`。所有 `self.classifier.get_xxx()` 调用改为使用传入的 `self._storage_details` / `self._storage_size`。`clear_selected()` 确认后 `self.accept()`，不调用 `classifier.clear_categories()`。新增 `get_selected_categories() -> list`。

`MainWindow.show_storage_clean_dialog` 改为接收数据，返回选中类别或 None。

`MainPresenter.clear_storage` 改为：先从 classifier 获取数据 → 传给 view → 收到选中类别后调用 `classifier.clear_categories()`。

### 步骤 3：_start_scanning 改名为公开方法（问题 5）

**文件**：`presenters/main_presenter.py`、`views/main_window.py`

**问题**：`MainWindow.on_recent_folder_selected` 调用 `self.presenter._start_scanning(folder_path)`（私有方法）。

**修复**：`MainPresenter._start_scanning` 重命名为 `start_scanning`。更新 3 个调用点：`on_unfinished_session_continue`、`on_folder_selected`、`MainWindow.on_recent_folder_selected`。

### 步骤 4：缓存构建逻辑下沉到 ClassificationManager（问题 6）

**文件**：`core/classification_manager.py`、`presenters/main_presenter.py`

**问题**：`MainPresenter.on_hash_finished` 和 `on_threshold_changed` 重复构建复杂的缓存结构（file_hashes、md5_hash_map），这是 Core 层职责。

**修复**：`ClassificationManager` 新增 `build_hash_cache(image_paths, groups, duplicates, hash_list=None) -> dict` 方法，封装缓存结构构建逻辑（包含文件元信息、相似分组、重复映射、文件哈希）。

`MainPresenter.on_hash_finished` 和 `on_threshold_changed` 改为调用 `self.classifier.build_hash_cache(...)`，移除内联的缓存构建代码。

### 步骤 5：清理死代码 Observer（问题 8+9）

**文件**：`services/classification_service.py`、`services/duplicate_service.py`

**问题**：两个服务继承 Observer 并 emit 多个事件，但无任何订阅者（仅 `HashAnalysisService` 的 Observer 真实使用，保留）。

**修复**：
- `ClassificationService`：移除 `from core.observer import Observer`、移除 `Observer` 继承、移除 `super().__init__()`、移除所有 `self.emit(...)` 调用（约 8 处）
- `DuplicateService`：同上（约 7 处 emit）

### 步骤 6：HashAnalysisDialog 减少直接状态访问（问题 7）

**文件**：`dialogs/hash_analysis_dialog.py`、`views/main_window.py`、`presenters/main_presenter.py`

**问题**：对话框直接读写 `hash_service.current_stage`、`hash_service.threshold`、`hash_service.image_paths`，并直接调用 `set_threshold`、`cancel`。

**修复**：
- 构造函数改为接收 `total_count: int` 和 `initial_threshold: int`，替代直接读取 service 属性
- 新增 `self._current_stage = 0` 本地跟踪阶段，`on_stage_changed` 中递增，`on_update_progress` 中使用本地值
- `on_threshold_changed` 移除 `self.hash_service.set_threshold(value)` 直接调用，仅 emit `threshold_changed` 信号（Presenter 的 `on_hash_threshold_changed` 回调已统一处理）
- 新增 `cancel_requested = pyqtSignal()`，`cancel_analysis` 和 `closeEvent` 改为 emit 此信号，Presenter 连接到 `hash_service.cancel`
- 保留 `showEvent` 中调用 `hash_service.start_analysis`（对话框管理自身生命周期，可接受）

`MainWindow.show_hash_analysis_dialog` 调整参数传递，并连接 `cancel_requested` 信号到 `hash_service.cancel`。

### 步骤 7：Presenter 职责整理（问题 10）

**文件**：`services/classification_service.py`、`presenters/main_presenter.py`

**问题**：`_apply_groups` 混合数据过滤与服务状态更新。

**修复**：`ClassificationService` 新增 `apply_similar_groups(similar_groups: list) -> list` 方法，封装"过滤已处理图片 + 未分组图片单独成组 + 设置 groups"的逻辑。`MainPresenter._apply_groups` 简化为委托调用。

注：`classify_image` 中调用 `HashAnalysisService.group_by_similarity`（无状态静态方法）保留，耦合度低，添加注释说明。

## 不修改项

- `FolderSelectDialog` 保持死代码现状（用户未明确决策，不冒险删除也不强制启用）
- `MainWindow.add_shortcut` 的 `QFileDialog` 使用保持现状
- `HashAnalysisService.run_analysis` 内部 `ImageScanner()` 实例化保持现状（可接受的内部依赖）

## 注释添加范围

1. **所有修改的方法**：添加 docstring 说明"做什么"和"何时用"
2. **分层边界公共 API**：Service 的公共方法、Presenter 对外方法、View 的回调接口
3. **缓存数据结构**：`build_hash_cache` 返回结构、`file_hashes` 字段含义
4. **调用方向**：分层边界处用注释标明，例如 `# View -> Presenter: 返回用户选中的删除项`

风格：中文 docstring，三引号，说明做什么/何时用；行内注释用 `#` 说明为什么；保持简洁，不解释明显的 UI 布局代码。

## 验证方法

每步完成后启动应用 `python app.py` 测试对应功能：

1. **步骤 1 后**：选择含重复图片的文件夹 → 哈希分析完成 → 点"查看"打开详情对话框 → 选中删除 → 确认 → 验证文件被删除、重复列表更新、状态栏显示"所有重复图片已处理完成"。再次扫描同一文件夹验证已处理记忆生效（重复组不再出现）。
2. **步骤 2 后**：点"清除存储占用" → 对话框显示各类别大小 → 选中类别 → 确认清除 → 验证对应文件被删除、快捷键列表更新。
3. **步骤 3 后**：从"最近文件夹"下拉框选择文件夹 → 验证扫描正常启动。
4. **步骤 4 后**：完成哈希分析 → 关闭重开应用 → 再次扫描同一文件夹 → 验证"文件无变化，使用缓存结果"。
5. **步骤 5 后**：分类、重复图片删除、哈希分析全流程回归测试。
6. **步骤 6 后**：哈希分析对话框显示 → 调整阈值 → 关闭对话框（触发取消）→ 验证主窗口状态栏更新、无残留线程。
7. **步骤 7 后**：完成哈希分析后切换分组、分类图片 → 验证分组正确更新。
